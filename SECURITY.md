# Security Policy and Responsible Disclosure

## Overview and Philosophy

**PrivateChat** is a self-hosted, invitation-only, end-to-end encrypted messaging application built for small, trusted groups. We take security seriously and welcome responsible vulnerability reports from the community.

Never claim that any application is 100% attack-proof. This document articulates our security architecture, trust boundaries, threat model limitations, and the process for reporting potential security issues.

## Threat Model and Security Guarantees

### What PrivateChat Guarantees

1. **End-to-End Cryptographic Confidentiality:**
   - Messages are encrypted on the sending device and decrypted only on recipient devices using standard modern primitives (X25519 for Diffie-Hellman key exchange, HKDF-SHA256 for key derivation, and ChaCha20-Poly1305 / AES-256-GCM for authenticated encryption).
   - The backend server acts strictly as an untrusted ciphertext relay. Plaintext message bodies and message encryption keys never touch server memory, logs, or disk.

2. **Tamper Proofing and Authenticity:**
   - Every message includes an Ed25519 digital signature over the ciphertext envelope signed by the sender's device private key. The server and recipients verify this signature.
   - Any message altered in transit will fail Poly1305 authentication and Ed25519 signature checks.

3. **Strict Invitation-Only Access:**
   - Registration is impossible without a cryptographically secure invitation code generated by the server Owner.
   - Invitations are hashed with Argon2id on the server, enforcing expiration times, single-use limits, and optional manual Owner approval for newly paired devices.

4. **Zero External Dependencies / No Third-Party Telemetry:**
   - No external CDNs, third-party analytics, cloud push notification services, or tracking scripts are bundled or loaded at runtime.
   - The server operates fully air-gapped on a local LAN or private VPN if desired.

5. **Defense-in-Depth Web Security:**
   - Strict Content Security Policy (CSP), HTTP Strict Transport Security (HSTS), X-Frame-Options (`DENY`), and X-Content-Type-Options (`nosniff`).
   - CSRF tokens validate all state-changing HTTP requests.
   - In-memory rate limiting mitigates brute-force attacks against authentication and invitation validation endpoints.

## Known Threat Boundaries and Residual Risks

When assessing the security of PrivateChat, consider the following honest limitations:

1. **Endpoint and Client Device Security:**
   - If a client device is infected with malware, a keylogger, or a malicious browser extension, private keys or plaintext messages displayed on screen can be compromised.
   - While private keys stored in IndexedDB are protected by Web Cryptography API vaults encrypted with the user's master password via PBKDF2/Argon2, a compromised OS or runtime memory inspection bypasses browser sandboxing.

2. **Metadata and Traffic Analysis:**
   - The server knows *who* sends a message to *which room* at *what time*, as well as user presence and IP addresses.
   - Traffic analysis can reveal communication timing between participants unless routed over a privacy network such as Tor or WireGuard.

3. **Origin Boundary Partitioning (GitHub Pages vs Self-Hosted Domains):**
   - In web browsers, IndexedDB and Web Cryptography storage are partitioned strictly by origin (`scheme://host:port`).
   - If users access PrivateChat via GitHub Pages (`https://<user>.github.io`) rather than a direct domain (`https://chat.domain.com`), device cryptographic keys generated on one origin **cannot** access storage on another origin. Each origin requires independent invitation pairing.

4. **Self-Signed Certificates on Local Networks:**
   - For home LAN access without a domain name, browsers may display self-signed certificate warnings. An active Man-in-the-Middle (MitM) attacker on the local network could theoretically intercept initial HTTP traffic if TLS warnings are blindly accepted without verifying certificate fingerprints.
   - We recommend using reverse proxies with Let's Encrypt (e.g. Caddy, Nginx, or Traefik) or establishing a private Tailscale / WireGuard mesh for secure remote access.

## Reporting a Vulnerability

If you discover a security vulnerability in PrivateChat, please follow responsible disclosure guidelines. **Do not create public GitHub issues or discussions for undisclosed security vulnerabilities.**

### How to Report:
1. Email your report privately to the project maintainer:
   - **Email:** `security@privatechat.local` (or submit a confidential security advisory via GitHub's "Security Advisories" tab on the repository).
2. Include the following details:
   - Type of vulnerability (e.g., Cryptographic flaw, Authentication bypass, CSRF, Injection).
   - Step-by-step reproduction instructions or a minimal Proof of Concept (PoC).
   - Component affected (client, server, shared crypto library, or WebSocket protocol).
   - Assessment of potential impact and suggested remediation.

### Response Timeline:
- **Initial Response:** Within 48 hours of receipt.
- **Triage and Status Update:** Within 5 business days.
- **Patch Release:** Coordinated security release before public disclosure.

Thank you for helping keep PrivateChat secure for everyone!
